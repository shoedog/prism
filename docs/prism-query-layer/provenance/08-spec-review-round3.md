## BLOCKERS

**B1 — `NavigationSession<'a>` / `Arc<'static>` contradiction (§3, §14)**
*Both lenses agree; Soundness confirmed, Rigor independently identified the identity ambiguity root.*

The struct definition in §3 carries `<'a>` (borrows `&'a LoadedRepo`, `&'a NavigationIndex`), but §14's `ResolverContext::Session(Arc<NavigationSession<'static>>)` requires `'a = 'static`. Neither `LoadedRepo` nor `NavigationIndex` are genuinely static. The R2-m3 resolution note names the correct variant but leaves the struct definition unchanged — the contradiction remains and is a compile-time error. This is structurally upstream of everything in §17; the build order cannot be followed until the ownership shape is fixed.

*Fix:* Remove `<'a>` from `NavigationSession` by owning data via `Arc`: `repo: Arc<LoadedRepo>, index: Arc<NavigationIndex>`. Update §3's struct block and §14's `ResolverContext` definition to match. The resolver trait bounds are unaffected.

## MAJOR

**M1 — Golden examples embed wrong line number (§8)**
*Soundness MAJOR; Rigor did not independently surface this (lens confusion on which spec to read).*

The §8 `callers` golden states `run_slicing_compat` at lines 210–240. Verified in the codebase: it is at line 269 of `algorithms/mod.rs`. If implementers hand-author fixtures from the spec's representative example, the fixture will embed a wrong range and the first CI run will fail with a confusing mismatch.

*Fix:* Either correct the example to line 269 (quick), or — preferably — add a sentence in §17 Step 5/6 stating: "Canonical golden fixtures must be generated by running the tool against the live repo; the §8 examples are illustrative only." The latter eliminates an entire class of staleness.

**M2 — Whole-repo ingestion: ignore-rule precedence and failure propagation are open questions (§5)**
*Rigor MAJOR; not directly addressed by Soundness.*

§5 defines the built-in skip list (.git/, target/, node_modules/, vendor/, dist/, build/) and `ParseFailed` exclusion, but leaves ignore rules as an open question (spec `:381-382`). Three gaps: (1) no defined precedence when a file matches .gitignore AND is a supported language AND fails parse; (2) no spec for how a read error or non-UTF-8 file in the middle of traversal affects a query (abort? warn? skip?); (3) no definition of whether `SkippedPath` warnings are surfaced in the `Evidence` envelope when a query touches a skipped file vs. when the skipped file was discovered at load time.

*Fix:* Define a total skip precedence order (e.g., explicit ignore > ParseFailed > built-in patterns > supported extension), state that per-file errors never abort a query, and confirm `SkippedPath` warnings appear in `Evidence.warnings` whenever the queried seed names a skipped file.

**M3 — CPG node model does not cover the promised navigation surface (§3, §7, §8)**
*Rigor MAJOR; Soundness noted the `ContainsStatement` gap but not the full mismatch.*

Current CPG nodes are Function, Statement, Variable only (`cpg.rs:390–416`). The spec's `nodes-at`, `module-deps`, and `repo-map` imply class-level, module-level, and import-level structural navigation. The ego-graph's `ContainsVariable`-only edge set (no `ContainsStatement`) is the correct spec-side acknowledgment, but the constraint should be stated at the query layer too: v1 `nodes-at` returns function nodes and enclosing functions only; class/struct/module nodes are not first-class and will not appear in results.

*Fix:* Add a v1-scope statement to §8's `nodes-at` spec: results are limited to `Function` and `Variable` nodes; class/struct/module resolution is deferred. This prevents implementers from expanding the node model unexpectedly and then discovering the CPG doesn't support it.

**M4 — Language precision boundaries are not defined (§10)**
*Rigor MAJOR; Soundness did not independently flag.*

Import extraction covers Python, JS, TS/TSX, Go. Rust, Java, C, C++, Lua, Terraform, Bash fall through (`ast.rs:295–303`). Call resolution admits stem-collision limits (`call_graph.rs:645–653`). The spec says "precision is heuristic" at §2/§10 but does not define what degraded output looks like per language or what the acceptance threshold is for nav integration tests.

*Fix:* Add a one-table appendix (or inline in §10) mapping each of the 11 languages to their expected v1 precision tier: exact (Python/JS/TS/Go), call-derived-only (Rust/Java/C/C++), unsupported-imports (Lua/Terraform/Bash). Nav integration tests must cover at least one degraded-precision language so the fixture encodes the expected warning, not silence.

**M5 — `CpgContext::scope` build path is unspecified (§17 Step 3)**
*Soundness MINOR upgraded to MAJOR here because silent misconfiguration produces an incomplete nav index.*

`CpgContext` has `scope: Option<CpgScope>` (`cpg.rs:65`) and a separate `build_scoped` constructor. If `build_scoped` is used at nav-index build time, the resulting CPG covers only the diff-scoped file subset and silently produces an incomplete whole-repo index with no error. The spec does not name which constructor to call.

*Fix:* Add one sentence to §17 Step 3: "Build via `CpgContext::build(files, type_db)` — `scope` will be `None`, indicating whole-repo coverage. Do not call `build_scoped` for the nav index."

## MINOR

**m1 — `line_range_index` O(log n) claim is inaccurate (§3, §7)**
*Soundness MINOR; Rigor did not surface independently.*

The innermost-enclosing query is O(log f + k) where f = file count and k = per-file nesting depth (in practice k ≤ 5). The "O(log n)" label in the spec is wrong for the whole-repo comparison — but the practical improvement over the confirmed O(n)-across-all-files `function_at` (`cpg.rs:1490`) is large and real. This is a label fix, not a redesign.

*Fix:* Replace "O(log n)" with "O(log f + k)" in §3/§7 commentary and any spec diagrams.

**m2 — CLI flatten gating produces a runtime error, not a clap parse-time error (§12)**
*Soundness MINOR; Rigor framed CLI as BLOCKER but that was lens confusion — Soundness's narrower framing is correct.*

With `#[command(flatten)] review: ReviewArgs`, `prism nav callers --diff x` parses successfully and is rejected at dispatch with an application-level error. `--help` implies `--diff` is valid under `nav`; `prism nav --help` shows a misleading flag set. The compat matrix in §16 will lock in the application-error stderr format rather than clap's, making future message changes look like regressions.

*Fix:* Either (a) add the exact application-error message to §16's compat matrix so the gate locks the right artifact, or (b) move to an explicit subcommand to surface incompatibility at parse time. Document the choice in §12.

**m3 — `all_test_files` count in §16 is wrong; CLAUDE.md's "3 copies" guidance is operationally correct**
*Both lenses flag this; Soundness resolution is more precise.*

The spec R2-m1 says "two `all_test_files` arrays; CLAUDE.md's '3 times' note is stale." There are in fact three arrays across three test functions: `all_test_files` at lines 106 and 325, and `test_files` at line 472 (a strict superset including source files). All three require updating when test files are added. CLAUDE.md's "3 copies must be updated" instruction is operationally correct even though the variable names differ.

*Fix:* Change §16's R2-m1 note to "3 arrays in 3 test functions (two named `all_test_files` at :106, :325; one named `test_files` at :472)." Do not mark CLAUDE.md stale — its update instruction is right.
