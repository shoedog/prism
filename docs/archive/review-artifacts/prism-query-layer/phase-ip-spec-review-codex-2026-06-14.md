**REFINED REVIEW**

Verified foundation: the architecture home is right. `CodePropertyGraph::build_impl` builds `CallGraph` before CPG assembly (`src/cpg/build.rs:134-137`), Step 5 materializes edges via `cg.resolve_call_site(site)` (`src/cpg/build.rs:349-379`), and `CpgContext` builds the registry afterward (`src/cpg/context.rs:63-65`). Nav also re-resolves through the same `CallGraph` path (`src/navigation/call_resolve.rs:15-25`). A CPG-only post-pass would not satisfy the spec’s caddy nav recall goal.

1. **BLOCKER - `Exact` is still semantically inconsistent.** The spec says interface/embedding edges are `Exact` (`docs/...dispatch-design.md:96`, `176-189`) while explicitly allowing name+arity-only satisfaction (`141-144`), pointer/value method-set union (`126-129`), and name-collision over-approx as Exact (`226`). That contradicts the “provably-possible targets” claim. Either make Go method-set/signature matching precise enough for that label, or use `NameOnly`/a new confidence for approximate interface and promotion results.

2. **BLOCKER - empty interface hits are contradictory.** §5 pseudocode returns `ResolutionOutcome::hit(...)` whenever `interface_impls.get(...)` succeeds (`159-166`), but §9 says an empty vector means `ExternalReceiver` (`222`). In code, `hit(Vec::new())` means no resolved edges and no drop reason (`src/resolution.rs:151-163`), so telemetry will also miss it. Specify that empty vectors are never stored, or add an explicit `ids.is_empty() => dropped(ExternalReceiver)` branch.

3. **BLOCKER - incremental cache cannot safely merge whole-program dispatch state as specified.** §7 says `build_direct_subset` recomputes embedding/interface dispatch (`197`), but that function only sees changed files (`src/call_graph.rs:777-919`) and is merged into cached state (`src/cpg/build.rs:173-191`). Promotion, interface satisfaction, and live-type pruning are whole-program relations. Recompute/replace dispatch maps after merge from the full merged graph/files, or disable partial CPG reuse for Go dispatch.

4. **BLOCKER - promoted-method telemetry has no storage contract.** §4 says promoted aliases must be “marked” (`114-117`), but §7 only adds `interface_impls` (`195-200`). Existing `owner_lookup` would treat an alias as a normal owner hit and P6-lite would relabel it to `TypedParam`/`ConstructorLocal` (`src/resolution.rs:412-420`). Add a concrete serialized marker such as `promoted_methods`, plus remove/merge/cache behavior.

5. **MAJOR - Go selector precedence is incomplete.** The spec covers equal-depth embedded ambiguity (`118-120`) but not direct method depth 0. If `S` defines `m` and embeds `E.m`, Go’s direct method should win. A naive alias would create multiple primary owners and demote through current `owner_lookup` logic (`src/resolution.rs:233-240`). Define depth order: direct first, then uniquely shallowest embedded, then ambiguous/drop.

6. **MAJOR - canonical Go type keys are undefined.** The spec uses bare `Runner` plus mentions `pkg.T` (`112`, `133-149`). Current import and owner normalization do not provide a package-stable key (`src/ast.rs:812-864`, `src/resolution.rs:75-83`). Define whether keys are package-qualified, file/package scoped, or intentionally bare-name over-approx, and add cross-package interface/embedding fixtures.

7. **MAJOR - RTA pruning can create false negatives.** The spec prunes whenever the global live set is non-empty (`145-149`), but Go live collection only sees composite literals (`src/live_types.rs:153-172`). `new(T)`, declarations, factories, or DI can make real implementers absent from `live` while some unrelated type makes `live` non-empty. Either make Go live collection conservative enough, or fall back to all satisfiers when intersection is empty.

8. **MAJOR - “arity” is underspecified.** §5.3 uses same parameter count (`141-143`) without defining grouped params (`F(a, b int)`), variadics, unnamed params, receiver exclusion, or return participation. Existing code has parameter helpers but no Go arity contract. Specify a normalized extraction algorithm and pin grouped/variadic/return-mismatch fixtures.

9. **MAJOR - `GoTypeProvider` divergence is left to happen.** §12 leaves `DispatchProvider` as a separate future API (`284-287`), but it already answers Go dispatch with different rules. Require `GoTypeProvider` and CallGraph dispatch to share `src/dispatch/go.rs`, or mark provider dispatch as deprecated until reconciled.

10. **MINOR - module wiring/checklist needs tightening.** The spec names `src/dispatch/go.rs` but not `src/dispatch/mod.rs` or root module registration (`src/lib.rs:32-58`). Also reword §2’s “CallGraph::build calls collect_live_types” to future tense.
