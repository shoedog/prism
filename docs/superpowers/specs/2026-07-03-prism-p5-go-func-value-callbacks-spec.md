## Problem (adjudicated recall holes — the top Go FN class in eval/adjudications.jsonl)

Prism has no function-value model for Go:
- **Registration invisible:** `Command{Run: emptyRun}` in cobra (7× adjudicated `prism_fn`), `EncodeCaller: ShortCallerEncoder` (zap `config.go:214`), and bare function identifiers passed as call arguments (`RegisterHandlerDirective(parseCaddyfile)`, caddy) create no edge. The gopls oracle counts these as incoming references; prism shows nothing.
- **Invocation drops:** `cmd.Run(args)` where `Run` is a func-typed struct field resolves to nothing. **Architecture fact (spec-review BLOCKER, honor it):** for Go RECOVERED receivers, `owner_lookup` miss enters the Go interface-consult arm (src/resolution.rs:1391-1432) and returns `dropped(ExternalReceiver)` there — it NEVER reaches the C-only free-function fallback at :1448. The invocation arm therefore lives INSIDE the interface-consult miss path, not at the C gate.

## Architecture constraints (from spec review — read before coding)

- **Nav call edges derive from `CallSite`s resolved by `resolve_call_site_full()`** (src/call_graph.rs:~236). A registration reference must NOT be modeled as a synthetic CallSite with `callee_name = helper` — it would resolve as `free_single`/**Exact** (a soundness hole). Registrations get a **dedicated registration index** on `CallGraph`, surfaced at nav query time as NameOnly edges.
- New serialized `CallGraph` state requires full plumbing: `CallGraph::empty`, `build_skeleton` (call_graph.rs:~389), the full builder (per-function loop ~:728) AND the direct-subset builder (~:2309 — both, or incremental/direct behavior diverges), `remove_files`, `merge`, and — if S1/S2 tables are whole-program derived like the Go interface data — an explicit clear/re-apply pass in the incremental rebuild path beside `apply_go_embedding_promotion`/`apply_go_interface_dispatch` (src/cpg/build.rs:~297, `build_incremental_with_scope_graph_inputs`). Plus: CPG `CACHE_VERSION` (src/cpg_cache.rs:~76), sidecar `NAV_CALL_EDGE_CACHE_VERSION` (src/navigation/call_edge_cache.rs:~10) including the sidecar's serialized structs if registration edges ride it, `ResolutionKind::as_str` arms, `DropReason` call-stats match arms, cache-version tests. Walk this list explicitly in your report.
- Cache merge rule: a parallel branch (P3) also bumps the cache versions; whichever lands second rebases and increments FROM the landed value.
- For determining the enclosing function of a registration site, do NOT invent a line-based lookup: prefer hooking into the existing per-function extraction walk in the call-graph build where a `caller_id` (`FunctionId`) is already in scope; `ParsedFile::enclosing_function(line)` / `function_node_spanning(line)` exist as fallbacks — if you use one, say which and why.

## Scope (three slices, in order; each TDD'd)

**S1 — func-typed-field index.** In the Go type provider (src/type_providers/go.rs, `extract_struct_fields` ~:483 keeps `(name, type_string)` and already handles multi-name declarations `a, b func()` by pushing the type for each name): record which struct fields are func-typed — `type_string` starting with `func(` (named-type indirection is out of scope; note it). Expose `(owner_identity, field_name) -> is_func_type` lookup following the pattern of existing provider→call_graph data flow (see how embedding/interface data reaches `apply_go_embedding_promotion` / `apply_go_interface_dispatch` in src/call_graph.rs). **Owner identity is package-scoped, not the provider's bare struct-name key** (re-review MAJOR-1: `GoTypeProvider` stores structs by bare name, go.rs:132/:342/:1448 — bare keys would let a registration in one package feed a same-named type in another). For bare `T`, scope by the declaring package; for `pkg.T`, resolve `pkg` via Go imports. Unknown/ambiguous owner identity → the fact may feed nav-only registration records at most, NEVER S3.

**S2 — registration index (the adjudication flipper).** During the Go per-function extraction walk (where `caller_id` is in scope), scan for these forms and record `RegistrationRecord { enclosing: FunctionId, target: FunctionId, site: {file, line, start_byte, end_byte} }` (byte range included for deterministic one-edge-per-site identity, re-review MINOR-2) in a new serialized `CallGraph` registration table:
   a. Composite-literal keyed field whose value is a bare function identifier AND the field is func-typed per S1 (`Command{Run: emptyRun}`). If S1 cannot type the literal (unknown struct), fall back to recording ONLY when the value identifier resolves unambiguously per the gate below — count these separately.
   b. Assignment to a func-typed field: `x.Run = emptyRun` — recover the LHS operand's type at the assignment site using the SAME Go receiver-binding machinery as recovered receiver calls (re-review MAJOR-2); record a field-keyed registration only when that owner type is uniquely recovered AND `(owner_identity, field)` is func-typed per S1; otherwise skip and count.
   c. A bare function identifier passed as a call argument (`Register(parseCaddyfile)`). Gate for ALL forms: the identifier must resolve to a known in-repo function via existing same-package/import resolution helpers (NEVER bare cross-package name matching), AND must not be shadowed — perform a real local-binding check against the enclosing function's bindings using the existing Go binding machinery (the same used by receiver recovery, src/ast.rs:~432 area); a shadowed identifier is skipped and counted. Do NOT use "same-file/same-package" as a shadow substitute (spec-review MAJOR).
   Surface registrations in nav: `nav_callers(target)` includes the registration site as a NameOnly edge with new `ResolutionKind::CallbackRegistration` (as_str `callback_registration`); `nav_callees(enclosing)` includes the target symmetrically. Wire this in **`NavigationIndex::build_resolved_call_edges()` (src/navigation/mod.rs:273)** — merge registration edges there deterministically so `queries::{callers,callees}` keep reading `direct_callers`/`direct_callees` unchanged (re-review MINOR-3); update the `NavigationCallEdgeIndex` sidecar serialization + version accordingly.

**S3 — gated invocation resolution (inside the interface-consult miss path).** In the Go interface-consult arm (resolution.rs:1391-1432): explicit ordering (re-review MINOR-1) — concrete `owner_lookup` first (unchanged), then the `interface_impls` lookup + arity filter (unchanged); ONLY when interface dispatch has missed or arity-filtered to empty, and before the `dropped(ExternalReceiver)` outcome: if S1 says `(recovered_recv_type, call_name)` is a func-typed field, resolve the call to the DISTINCT registration targets recorded for that field. Note: S2 records are keyed by target/enclosing for nav, so ALSO key registrations by package-scoped `(owner_identity, field_name)` where knowable (forms a and b know the field; form c does not — form-c records carry no field key and NEVER feed S3; ambiguous-owner records likewise never feed S3). `1..=3` distinct targets → `demoted(..., ResolutionKind::FuncValueField)` (as_str `func_value_field`, NameOnly). `>3` → keep the drop but classify as new `DropReason::FuncValueFanout` (call-stats bucket). Zero known registrations → existing `ExternalReceiver` drop unchanged. Unrecovered receivers: unchanged.

**Telemetry.** call-stats (src/navigation/queries.rs:274-311): `func_value_field` lands in kind_nameonly automatically (it flows through resolver outcomes), but **`callback_registration` does NOT** (re-review MAJOR-3: call-stats iterates `cg.calls` + resolver outcomes only, queries.rs:200/:222) — iterate the registration table explicitly and increment `kinds`, `kind_nameonly`, and `demoted_edges` for it.
