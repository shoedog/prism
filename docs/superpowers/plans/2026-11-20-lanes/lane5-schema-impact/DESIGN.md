# Lane 5: schema-aware service impact — design

Status: design for the feasibility study is final; the pilot design is provisional until the feasibility memo
(`FEASIBILITY.md`, section 6) exists. Research record: `~/prism-evidence/lanes-2026-11-20/research/lane5-schema-impact.md`.

## 1. Intent

Answer one question that a single-repository call graph cannot: "this API operation or field changed: which
service handlers produce it and which client code consumes it?" The first user is a reviewer of the producer
change (and later the cross-service contract analyzer of the tooling roadmap). The output is a list of code
locations in the producer and consumer repositories, each tied to a schema version and a repository
revision.

This is the least certain of the four lanes. The lane therefore has two funded parts with an owner gate
between them: a 3 to 5 day feasibility study that measures whether the bindings can be recovered and whether
history shows the report would have helped, and a 15 to 25 day pilot that only starts on an owner go-ahead.

Candidate pairs on this machine:

- **Public pair P: `bench-repos/apache-answer`** (pinned at 6744295f). A Go (gin) server and a TypeScript
  React client in one repository. `docs/swagger.json` and `docs/swagger.yaml` are committed (Swagger 2.0,
  generated by swaggo; 161 paths; 204 commits touch the YAML). Handlers carry swaggo annotations
  (`// @Router /answer/admin/api/api-key/all [get]` directly above the method, `@Success 200 {object}
  handler.RespBody{data=[]schema.GetAPIKeyResp}`): 199 `@Router` lines. The client calls a hand-written
  wrapper (`request.get('/answer/api/v1/...')`): 111 call sites, 90 with a string literal and 9 with a
  template literal as the URL, plus 74 `useSWR` uses. Route registrations build their prefix across files
  from a configuration value (`r.Group(uiConf.APIBaseURL + "/answer/api/v1")`).
- **Private pair R: `pilot-producer` and `pilot-consumer`.** A real producer and consumer of the same
  product (every first URL segment the client calls is declared by the server). It does not have the shape
  the proposal assumed: the producer is code-first (routes are declared in route tables; its OpenAPI document
  is generated at run time and is not committed), and the consumer builds most URLs from template literals in
  largely untyped code. Details are in the private bindings file.

Three statements in the older roadmap (`04-prism-plan-roadmap.md` §4) do not hold and are not design inputs:
route strings are not available from existing records; Terraform is not a precedent for non-code graph nodes
(`TerraformRefGraph` has no consumer); the navigation index is not independent of the CPG cache.

## 3. Goals, non-goals, anti-goals

Goals:

1. For one schema format (OpenAPI, including Swagger 2.0) and one pair, bind schema operations to producer
   handlers and to consumer call sites, and report the code locations affected by a schema change.
2. Every binding states how it was established and whether it is unique. Everything that could not be bound
   is listed with a reason. The report never implies coverage it does not have.
3. Every artifact records the repository revision and the schema hash it was computed from, and a join of
   artifacts computed from different schema hashes says so.
4. The feasibility study produces numbers and ten rendered example reports from real history, so the owner
   can judge payoff before funding the pilot.

Non-goals (this lane): graph federation, a manifest of many repositories, MCP tools, new `Evidence`
variants, protobuf and gRPC, event schemas, semantic judgement of whether a change is safe, notifications to
consumer repositories, YANG/NETCONF/gNMI (to follow demonstrated demand), and closed vendor device firmware
(the roadmap places that in an acceptance and fault harness outside prism).

Anti-goals: a report that looks complete while silently dropping dynamic URLs; a binding grade that reuses
the word `Exact` (that grade means static call binding in prism and must not be diluted); product-crate
changes before the owner go-ahead.

## 4. Approaches considered

**A. Boundary nodes inside the code property graph** (the roadmap's sketch: `CpgNode::SchemaElement`, new
edge kinds, a `BoundarySlice` algorithm, nav queries). Pays off for federation later. Cost now: a cache
format change, new variants in closed enums, MCP goldens, and schema parsing inside the core crate, all
before anyone knows the bindings are recoverable. Rejected for the pilot.

**B. A separate workspace crate that reads prism's parsed files and call graph and writes its own JSON
documents.** `crates/prism-boundary` depends on the `prism` core library. It keeps schema parsing and new
dependencies out of core, touches neither the cache nor the navigation model, and can be deleted if the
pilot fails. A producer and a consumer are bound independently, each to a document; the impact step joins
documents and needs no repository access. That join is the seed of federation without building federation.
**Chosen for the pilot.**

**C. Scripts outside the product** (Python under `eval/`, using tree-sitter bindings and prism's CLI
output). Fastest way to measure recoverability and to replay history; not a product. **Chosen for the
feasibility study only.** Its replay harness is kept as the pilot's acceptance gate.

A fourth idea, delegating everything to existing tools, does not answer the question: `oasdiff`, `buf
breaking` and Pact compare schemas or contracts but do not locate handler and client code. They are useful
as the source of the changed-element list, which is why the impact step accepts one from outside (5.2).

## 5. Architecture (pilot; provisional)

```
schema file @ rev ──► SchemaIndex ──┬──────────────► diff(old,new) ──► changed elements ─┐
                                    │                                                     │
producer repo @ rev ──► bind ──► bindings document (role: producer) ─────────────────────┤──► impact document
consumer repo @ rev ──► bind ──► bindings document (role: consumer, with callers) ───────┘
```

### 5.1 Element identity

An element id is a string, stable across repositories. Two implementations (the Python prototype and the
pilot crate) must produce identical ids; the prototype writes a golden `ids.tsv` for the pinned schema and
the pilot's tests reproduce it byte for byte.

**Operations:** `op:<METHOD> <path>`.

| Rule | Example |
|---|---|
| Only the keys `get`, `put`, `post`, `delete`, `options`, `head`, `patch`, `trace` of a path item are operations; the method is upper-cased | `op:GET /a` |
| The base is `basePath` (Swagger 2.0) or the path part of the first server URL after dropping scheme, host and any `{variable}` segments (OpenAPI 3). A base of `/` or empty adds nothing. Base and path are joined with exactly one `/`; repeated slashes collapse | base `/api`, path `/x` → `/api/x` |
| No trailing slash, except the root path, which is `/` | `/a/` → `/a`; `/` → `/` |
| Every `{name}` becomes `{}`; a segment that mixes text and a parameter keeps its text | `/a/{id}` → `/a/{}`; `/f/{id}.json` → `/f/{}.json` |
| No percent-decoding and no case change in the path | |
| Two paths with the same id: keep the one whose original path string sorts first, and warn | `/a/{id}`, `/a/{name}` |

`operationId` is carried as an attribute, never as identity.

**Fields:** `field:<owner>#/<property path>`. Field ids are scoped to an owner and a property path never
crosses a `$ref`, so recursive schemas need no special case.

| Schema shape | Id |
|---|---|
| property `b` of named definition `A` | `field:A#/b` |
| property `c` of an inline object under `b` | `field:A#/b/c` |
| property `x` of the objects in array property `items` | `field:A#/items/[]/x` |
| `additionalProperties` holding an object with property `x` | `field:A#/*/x` |
| property `b` whose schema is `$ref: B` | `field:A#/b` only; `B`'s own properties are `field:B#/…` |
| `allOf`: members flattened in order into the owner; a later member's property replaces an earlier one of the same name; a `$ref` member contributes the referenced definition's properties under the owner | the swaggo envelope `allOf: [{$ref: RespBody}, {properties: {data: {$ref: X}}}]` gives `…#/code`, `…#/data` |
| `oneOf` / `anyOf` | the union of the members' properties, with a warning |
| an inline (unnamed) response or request body | owner `resp:<METHOD> <path>:<status>` or `req:<METHOD> <path>`, for example `field:resp:GET /a/{}:200#/data` |

`definitions_of(operation)` is the set of named definitions reachable through `$ref` (transitively) from the
operation's request body and its 2xx response bodies. Path, query and header parameters are not fields.

Reserved for a later format, not built: `rpc:<package.Service>/<Method>`, `msgfield:<package.Message>#<number>`.

### 5.2 Documents

Two JSON documents, each with a schema under `docs/contracts/` (`boundary-bindings.schema.json`,
`boundary-impact.schema.json`), versioned `0.x` while the lane is a pilot.

Bindings document (one per repository and role):

```json
{
  "schema_version": "0.1",
  "tool": { "name": "prism-boundary", "version": "…", "build_identity": "…" },
  "repo": { "name": "apache-answer", "rev": "<git sha>", "dirty": false },
  "schema": { "path": "docs/swagger.json", "format": "swagger-2.0", "sha256": "…", "info_version": "…" },
  "role": "producer",
  "bindings": [
    { "element": "op:GET /answer/admin/api/api-key/all",
      "via": "swaggo_annotation",
      "grade": "bound",
      "site": { "file": "internal/controller_admin/e_api_key_controller.go", "line": 49 },
      "function": { "file": "…", "name": "AdminAPIKeyController.GetAllAPIKeys", "start_line": 50, "end_line": 53 },
      "evidence": "@Router /answer/admin/api/api-key/all [get]",
      "callers": [] }
  ],
  "unbound": [
    { "kind": "operation_without_producer", "element": "op:…" },
    { "kind": "client_call_without_operation", "site": { "file": "…", "line": 0 }, "reason": "dynamic_url" }
  ],
  "counts": { "operations": 0, "bound": 0, "candidate": 0, "unbound": 0 }
}
```

Impact document: `change` (old and new schema hash, the list of changed elements with a change class),
`impacts` (per changed element: producer bindings, consumer bindings with their recorded callers), and
`warnings` (for example `schema_mismatch` when a bindings document was computed against a schema hash other
than the change's old hash, and `rev_dirty`).

The impact step takes the changed elements from its own structural diff of two schema files, or from a
caller-supplied list (`--changed elements.json`), so `oasdiff` or `buf` can be the differ.

### 5.3 Producer adapters

| Adapter | Evidence | Grade | In the pilot |
|---|---|---|---|
| `swaggo_annotation` (Go) | a `@Router <path> [<method>]` line in the comment block directly above a function or method declaration | `bound`: the annotation is what the schema was generated from | yes |
| `go_struct_field` (Go) | a struct `T` in package `p` with a field tagged `json:"name"` ↔ `field:p.T#/name` | `bound` | yes, if field level is in scope (F3) |
| `gin_registration` (Go) | `<group>.<METHOD>("<literal>", <handler>)`; the group prefix is resolved only through string literals in the same function | `bound` with a full literal path, else `candidate` on a path-suffix match | only if F1 shows annotations do not cover the operations |
| `python_decorator` | the Flask and FastAPI decorator sites prism already finds, with the path and method read from the decorator arguments | `bound` | only if the pilot pair has a Python producer |
| `route_table` (Node) | object literals `{ method, path, … }` in a registered route array | `bound` | last slice, for pair R, if the owner chooses it |

For a code-first producer with no committed schema (pair R), the route table can itself act as the schema
source: operations come from the producer's route entries at each revision, and the change list is the
difference between two revisions' route sets. This gives operation-level impact with no OpenAPI file. It is
an option the memo evaluates, not a commitment.

### 5.4 Consumer adapters (TypeScript and JavaScript)

- **Client calls.** A call is an HTTP client call when its callee is a method of a configured client object
  or one of the built-ins (`axios.<verb>(url)`, `fetch(url, { method })`), and the receiver binds to an
  import of the configured module that the file never rebinds. Clients are declared, not inferred:

  ```toml
  # prism-boundary.toml in the consumer repository, or passed with --config
  [[client]]
  module = "@/utils/request"      # import source
  export = "default"
  methods = { get = "GET", post = "POST", put = "PUT", delete = "DELETE", patch = "PATCH" }
  url_arg = 0
  base_path = ""                  # prefixed to every URL before matching
  response_root = "data"          # the part of the schema's response body the client hands to callers:
                                  # here the wrapper returns body.data, so client reads are matched against
                                  # the fields under `data`; "" when the client returns the whole body

  [[client]]
  hook = "useSWR"                 # key-first hooks: argument 0 is the URL, method is GET
  url_arg = 0
  ```

- **URL pattern.** A string literal is taken as written. In a template literal, a `${…}` that fills a whole
  path segment becomes `{}`; a `${…}` inside a segment or before the first `/` makes the URL `dynamic`.
  Concatenations of literals and expressions follow the same rule. The query string is cut. A URL held in a
  `const` that is initialised once in the same function or at module level is followed one step.
- **Matching.** Segment by segment against operations with the same method and the same number of segments.
  Two literal segments must be equal; a `{}` on either side matches anything. A match's score is the number
  of positions where both sides are equal literals or both are `{}`. One matching operation → `bound`.
  Several → the highest score if it is unique (so `/user/${id}` binds to `/user/{}` and `/user/me` binds to
  `/user/me` when both operations exist), else every top match as `candidate`. None → `unbound` with a
  reason. In a conditional URL with a `null`, `undefined`, `false` or empty-string arm (the key idiom of
  data-fetching hooks), the other arm is the URL.
- **Callers.** Each consumer binding records the functions that reach its call site through prism's call
  graph (`prism::api::callers`, depth 2 by default, Exact edges only), so the impact step needs no
  repository.
- **Hooks and fetchers.** For a key-first hook the hook call is the binding. A client call inside the
  hook's inline fetcher argument, and a client method passed as the fetcher, are not separate call sites.
- **Field reads** (scope decided by F3). From the call result, forward along prism's data-flow edges to
  member reads; a read `x.a.b` is matched to the field `a/b` under the configured `response_root` of the
  bound operation's 2xx response. The pilot crate reads edges through a new facade function in the core
  crate (`prism::api::dfg_edges`, the records `nav dfg-stats --edges` prints): the graph itself is not
  public outside the core crate.

### 5.5 Grades

`bound`: static syntax identifies exactly one element. `candidate`: more than one element fits. Anything
else is `unbound` and listed. A consumer of the report notifies only on `bound`. These words are separate
from `Exact`/`NameOnly`, which keep their meaning for call edges.

### 5.6 Revisions and schema versions

`repo.rev` is `git rev-parse HEAD`, `repo.dirty` is true when `git status --porcelain` is non-empty for
tracked files; `schema.sha256` is the hash of the schema file's bytes; `schema.info_version` is the schema's
own version string when present. The impact step refuses nothing but warns on every mismatch, because a
consumer that vendors no schema is always bound against a schema taken from the producer.

### 5.7 Where the code lives

- Feasibility: `eval/schema_impact/` (a package in the existing `eval` uv project, entry point `schema-impact`).
  No product crate changes.
- Pilot: `crates/prism-boundary` (library `prism_boundary`, binary `prism-boundary`), a workspace member
  outside `default-members`, depending on `prism`. JSON schema files only in the pilot (a YAML schema is
  converted by the caller), which avoids choosing a YAML dependency now. It uses `prism::api::nav_session`
  and `prism::api::callers`, and reads parsed files through the session (they are public). Data-flow edges
  are not reachable from another crate today; the field-read slice adds a facade function for them
  (section 5.4). Any non-facade public module it uses is listed in its README as a facade candidate.

|---|---|---|

## 9. Risks and accepted limits

- **History may show no late fixes.** A monorepo that regenerates its schema and updates its client in the
  same change gives the report little to catch. G3's second arm (the owner reads ten reports) exists for
  that case, and F5 exists because the owner's real pair lives in two repositories, where late fixes are
  more likely than in P.
- **Dynamic URLs.** URLs built by helper functions or from configuration cannot be matched statically.
  They are counted and listed as `unbound: dynamic_url`; the configuration can map known builders later.
- **Annotation drift.** A swaggo annotation can be stale relative to the registration. F1's cross-check
  measures how often; the pilot reports disagreement as a warning when both adapters are enabled.
- **Field names are matched by spelling** under the configured `response_root`. A client that renames fields in a
  mapper is out of model; such reads are missed, not mis-bound.
- **Parameter-position literals** (`/user/me` against `/user/{}`) can match the wrong operation when a
  literal route also exists; the matcher prefers the literal operation and grades ties `candidate`.
- **Out of model, as everywhere in prism:** URLs assembled at run time, reflection, generated clients not
  present in the repository.
