# C2-M2 readout: streaming the CPG cache

Experiment M2 of the shared-daemon lane (plan:
`docs/superpowers/plans/2026-10-12-shared-prism-daemon/C2-M2-cache-streaming.md`). It asks whether streaming the
CPG cache file, instead of holding the whole index clone and the encoded file in memory, lowers the peaks without
making load or build slower. The comparison tables are generated by `scripts/memreport/memreport.py compare
--experiment m2`; everything else here is written by hand.

The load half's memory win is real and repeatable (P1 separated in every corpus of both pairs, effect 156–733 MiB);
it is its load time that fails the rule. Whether a one-time load that is 1–3 s longer on prometheus (about 14 s
today) is worth a 731 MiB lower load peak on a shared daemon, which loads once per repository, is a change to the
pre-registered rule and is the owner's to make. It is not taken here.

**Owner decision, 2026-10-14:** override the rule and ship the load half ("agree on overriding and shipping"), and
accept the save half's unresolved P4. The load half merged as #389 (`9d5a67bc`), with new cache file names so that
older binaries never write a mapped file.

## The runs

Binaries (built 2026-10-13 evening; sha256 in the evidence directory's `bin/COMMITS-6am.txt` and `SHA256SUMS`):
`main` = `e7dc1cc2` (the save half's base), `save` = `9f1e28b2` (the save half's encoding path, without the lock
file that #380 added later; the lock does not touch the write), `load` = `91e5a5af` (save half + `memmap2 =0.9.8`
reader). Corpora: slicing (`7db8f195`), excalidraw (`0642e72c`), prometheus (`505095b6`); ruff left out for time,
as the procedure says (the gate needs two corpora).

1. Load half: `--kinds warm,workload --reps 3`, interleaved save-1, load-1, save-2, load-2 (07:01–07:40 MDT).
2. Save half: `--kinds build --reps 3`, interleaved main-1, save-1, main-2, save-2 (07:40–08:56 MDT).

No run was excluded. Hand check (plan Step 4): prometheus load time and load peak recomputed from
`raw/prometheus/warm-{1,2,3}.json` (`after_index` minus `after_load_repo`) for q-save-1 and q-load-1 match the
comparison to the millisecond and the 0.1 MiB.

## Host state: this was not a quiet window

The run was scheduled for 06:00 MDT as a quiet window. It was not one:

- 06:00–07:00: the procedure's 60-minute wait. A bridge container from another session was busy at 06:00 and host
  builds appeared at 06:40–06:50 (`6am-quiet-wait.txt`). At 07:00 nothing was building and the containers were
  idle, so the run started; the procedure says to run anyway after 60 minutes and say so.
- Throughout: Chrome and Codex-app renderer processes spinning at about 100 % CPU each (for days), putting the
  1-minute load average near 20 with nothing else running. The owner had Chrome quit at about 08:43, during the
  last run (qb-save-2).
- From 08:40 the owner's work in another lane (OrbStack at about 740 % CPU, load average 36) overlapped qb-save-2,
  the save side of build pair 2. Its main side (qb-main-2) ran before. **Pair 2's build times are therefore
  confounded and P4 rests on pair 1 alone**, whose save side also ran at a higher load (median 36.6 against 29.7).
- 1-minute load average medians per series: load half 25.4 / 26.7 (pair 1), 27.2 / 25.6 (pair 2); save half 29.7 /
  36.6 (pair 1), 24.5 / 25.0 (pair 2). Swap in use 8.7 GB of 10 GB throughout. Per-run boundaries with load and
  swap: `6am-load.txt`.

Peaks were stable under this load (ranges within 1–5 % of the median, as in the earlier loaded runs); times were
not (excalidraw build 37–67 s for one binary within one series). The time verdicts above should be read with that.

## What was not measured

- ruff (first build 20+ minutes per run).
- The merged save half itself (#380, with the lock file); `bin/save` is its encoding path without the lock.
- Build time on a host with nothing else running.
